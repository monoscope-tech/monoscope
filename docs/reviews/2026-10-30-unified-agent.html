How the shared agent works

Slack, web, issue chat, and scheduled tasks are moving onto the same tools, saved progress, and result handling.

Background work should not need constant approval.That is the target. Shared event authority and complete action recovery remain release boundaries.

Four entrances. One shared core.

The entry points still handle their own protocol. The important change is that they reuse the same agent underneath.

2

Use one executor and tool catalog

Check current access, call existing operations, and save progress as the agent works.

3

Retain results and deliver the answer

All durable entry points use one completion transaction. Slack retains its delivery receipts; native business mutations still need the shared action ledger.

“Shared core” does not mean deleting Slack signature checks, delivery receipts, or the specialized code-review verifier.

Change a tool once

The API and agent reuse the same operation instead of maintaining competing handlers.

Resume after an interruption

A retry can reuse completed reads and the original model request.

Keep user decisions intact

An old request does not reactivate a paused routine or restore a deleted conversation.

Uncertain actions stop the turn.The agent retains action identities and known responses. Artifact writes commit with their outcomes; opaque API and external actions stop on uncertainty. This does not claim universal exactly-once execution.

What stays specialized

Slack: signed events, account linking, message delivery, and delivery reconciliation.

Code review and fixes: VM lifecycle, frozen tests, verifier proofs, and the review/fix state machine. Their domain records still need typed links to the common run ledger.

Evidence access: A restricted read raises the whole conversation’s requirement. Saved answers, documents, copied instructions, and later model turns keep that requirement. Shared Slack and wiki destinations do not inherit an administrator’s private access.

Request identity: Native event recovery retains its original member after a routine owner change. Tools use the lower current owner/requester role and saved role limit before execution. A role upgrade applies to new work; retries retain their limit. The run inspector shows that limit. An explicit restart uses the current owner; Slack requests stay bound to their sender. Busy-thread steering accepts only the current run’s requester; other members keep their own pending requests.

Migrations: Applied SQL filenames and checksums stay unchanged. Group remaining unapplied schema changes per implementation slice. One indexed evidence lookup serves the runtime and database triggers; a 5,000-run temporary-table update fell from 15.0 s to 0.29 s.

Storage: immutable run evidence, editable conversation documents, and versioned project knowledge keep their different lifetimes.

04

What’s ready, and what isn’t

The consolidation is real, but the full autonomous agent is not finished.

Already in the code

  • One catalog for API and agent-only tools.
  • Shared checkpoints for Slack, web, issue chat, and scheduled conversations.
  • One completion transaction for chat, schedules, Slack, enrichment, and review.
  • Current-member, pause, and request-identity checks.
  • Shared evidence requirements for conversations, documents, titles, and retained runs.
  • One action ledger for catalogued tools, typed recovery outcomes, and action history.
  • Shared capability checks for tools, native issue metadata, and GitHub publication.
  • Native issue changes commit with their run result; Observe reviews retain analysis without a GitHub write.
  • Persisted routine policies, scheduled Autonomous defaults, and conservative adoption.

Next before broader autonomy

  • Complete event authority and optional selected action review.
  • Complete native wiki authorization, reconciliation, and broader Slack evidence audiences.
  • Link native mutations to the common action ledger and recover older stranded runs.
Autonomous is the intended default for newly enabled routines.The design does not require approval for every action. Optional review applies only to explicitly selected kinds of action.
